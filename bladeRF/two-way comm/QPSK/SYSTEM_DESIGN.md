# EN2130 — Two-Way SDR Communication System — Design Document

Ground-up redesign, built for two ANTSDR E200 (Pluto-compatible / libiio) nodes, ignoring the
prior bladeRF/Pluto prototype. This document is the reference for both the GNU Radio flowgraphs
and the Python application layer delivered alongside it.

## 1. Requirement traceability

| Brief requirement | Where it's satisfied |
|---|---|
| Message delivery via digital modulation (BPSK/QPSK) | QPSK, differential-coded, RRC-shaped — GNU Radio PHY chain (§3) |
| Unique user addressing | `dest_id`/`src_id` fields, checked in GNU Radio's Frame Parser + Address Filter block (§4, §6) |
| Acknowledgment (ACK) on receipt | Auto-generated by the same block, transmitted back over RF within the same flowgraph (§6) |
| CRC-based error detection, discard corrupted | `digital_crc32_async_bb` (check mode) on every received frame, before address filtering (§3, §4) |
| Two transceivers, real two-way link | FDD: each node's flowgraph runs a TX and an RX chain concurrently on two different frequencies (§2) |
| Packetization and reassembly of payloads | 7-byte header + fragmentation in `link_layer.py` (§5, §7) |
| Supported payloads: text, image, audio | `link_layer.py` fragments/reassembles arbitrary bytes; `flet_chat.py` handles the three payload types (§7, §8) |
| Application on top of the core system | Extended Flet chat app (§8) |
| Bonus: encryption | Fernet (already in your codebase), applied before fragmentation (§7, §8) |

## 2. Physical layer plan — FDD, two frequencies

Each ANTSDR E200 runs one TX chain and one RX chain **simultaneously**, on two different
frequencies, so neither node ever has to detect/avoid its own or the other node's transmissions:

```
Node 1:  TX @ f1 ───────────────►  RX @ f1
         RX @ f2  ◄─────────────── TX @ f2      Node 2
```

| Variable | Node 1 | Node 2 | Notes |
|---|---|---|---|
| `tx_freq` | `f1` = 433.0 MHz | `f2` = 438.0 MHz | placeholders — set to whatever slot your lab assigns |
| `rx_freq` | `f2` = 438.0 MHz | `f1` = 433.0 MHz | |
| `samp_rate` | 2 MHz | 2 MHz | matches your earlier working design |
| `sps` | 4 | 4 | → symbol rate 500 ksym/s |
| occupied BW (α=0.35) | ≈ 675 kHz | ≈ 675 kHz | 5 MHz spacing between f1/f2 is a comfortable guard band |

Why FDD instead of a single shared frequency: with two dedicated channels, TX and RX run
continuously and independently — no carrier-sense/CSMA logic, no TDMA switching state machine, no
risk of a node jamming its own receiver. This removes an entire class of bugs a 2-week-review
project timeline doesn't need to spend budget on. If your lab only assigns **one** frequency slot,
tell me and I'll convert this to a half-duplex TDMA variant (same packet format, different MAC
timing).

## 3. PHY chain (per node, both directions use the same design)

**Modulation:** QPSK, differential-coded (`differential=True`), Gray-mapped, RRC pulse shaping
(`excess_bw = 0.35`), `sps = 4`. Differential coding is kept specifically because a 4th-order
Costas loop has a 90°-rotation ambiguity that plain QPSK slicing can't resolve — this is proven in
your existing prototype, so it's carried over unchanged.

**TX chain:**
```
UDP-in (from link_layer.py, port 52001)
  → CRC32 add
  → preamble/pad  [128× 0x55 dummy + 4-byte access code 0xAC 0x62 0x0D 0xCD]
  → PDU → tagged stream
  → QPSK modulator (differential, RRC α=0.35, sps=4)
  → IIO Pluto Sink @ tx_freq
```

**RX chain:**
```
IIO Pluto Source @ rx_freq
  → DC blocker
  → (RRC matched filter — see note below)
  → Symbol Sync (Mueller & Müller, sps=4)
  → Costas Loop (order 4)
  → Constellation Decoder (QPSK)
  → Differential Decoder (mod 4)
  → Map → Unpack bits
  → Correlate Access Code (tags frame start)
  → Pack bits → Tagged Stream Align → Stream-to-Tagged-Stream → PDU
  → Frame Parser + Address Filter + Auto-ACK  (epy_block, §6)
  → UDP-out (to link_layer.py, port 52002)      [both data frames and ACK frames]
                                                  ↳ ACK frames also loop back into
                                                    this node's own TX chain (fan-in
                                                    before the CRC32-add stage)
```

**Missing-matched-filter note:** the TX modulator applies an RRC transmit filter, but nothing
in the RX chain applies the matching RRC receive filter — `Symbol Sync`'s MMSE resampler does
timing interpolation only, it is not a matched filter. Add a **Root Raised Cosine Filter**
(Filters palette in GRC — this auto-creates the correct tap-generator + FIR-filter block pair,
which is safer than a hand-authored one) between the DC blocker and Symbol Sync, with
`alpha=0.35`, `sym_rate = samp_rate/sps = 500e3`, `samp_rate = samp_rate`. Functionally the chain
runs without it (your prior prototype did), but SNR and adjacent-channel rejection improve
noticeably with it — treat it as a bring-up-after-first-contact step, not a blocker.

**Access code:** reused unchanged from your working design — `0xAC 0x62 0x0D 0xCD`
(`10101100011000100000110111001101` as a 32-bit correlation string), `threshold=4`. It was already
validated over real hardware; no reason to change it.

## 4. Packet header (wire format, 7 bytes, all fields unsigned bytes)

```
Offset  Field       Meaning
0       dest_id     destination node ID (255 = broadcast)
1       src_id      sender's node ID
2       msg_id      logical message counter (wraps mod 256), assigned by the sender
3       frag_idx    0-based fragment index within this msg_id
4       frag_tot    total fragment count for this msg_id (1 if it fit in one frame)
5       type        0=TEXT  1=IMAGE  2=AUDIO  3=ACK
6       len         payload length in this fragment (bytes)
7..     payload     `len` bytes
```
followed by the 4-byte CRC32 that `digital_crc32_async_bb` appends automatically. Maximum
fragment payload is capped at 180 bytes, keeping every on-air frame short (header + payload + CRC
≤ 191 bytes ≈ 764 bits ≈ 1.5 ms airtime at 500 ksym/s — negligible compared to ACK round-trip
latency).

An ACK frame is just this same header with `type=3`, `frag_tot=1`, `len=0`, and `frag_idx` set to
the fragment index being acknowledged — no payload bytes at all.

## 5. Why fragmentation/ARQ live in Python, not inside GNU Radio

GNU Radio owns exactly one job on the MAC side: **given a frame that arrived, is it valid and is
it for me, and if so, ACK it.** That's CRC-check → address-check → auto-ACK, all inside one
`epy_block`, all visible as GNU Radio behavior you can point to in a demo/viva.

Everything above that — assigning `msg_id`, splitting a 40 KB image into ~220 fragments, tracking
which fragments are outstanding, retrying on timeout, reassembling out on the far end — is state
that persists across many packets and involves real timers. That's much easier to write, unit
test, and debug as ordinary Python (`link_layer.py`) than as an embedded block inside a running
GNU Radio scheduler, where your only debugging tool is `print()` redirected around GRC's log
capture (as you'd already discovered). It also splits cleanly across a 4-person group: two people
can own the GRC flowgraph, two can own `link_layer.py` + the UI, and both halves only need to
agree on the 7-byte header — a much smaller integration surface than sharing one `.grc` file.

## 6. MAC behavior — the RX-side `epy_block` (Frame Parser + Address Filter + Auto-ACK)

```
on frame arrival (already CRC-verified upstream):
    parse 7-byte header
    if dest_id not in {my_id, 255}:
        drop                                   # "unique addressing" requirement
        return
    forward full frame (header+payload) → UDP out to link_layer.py   # both data and ACK types
    if type != ACK:
        build ACK: [src_id→dest, my_id→src, same msg_id, same frag_idx, frag_tot=1, type=ACK, len=0]
        publish ACK → local TX chain (fan-in before CRC32-add)        # "ACK mechanism" requirement
```
Note the ACK is generated and physically transmitted **inside the same node's own flowgraph** —
this is the piece that was silently broken in the earlier bladeRF/Pluto split (RX-only and TX-only
were separate processes with no path between them). A single symmetric flowgraph per node avoids
that class of bug entirely.

## 7. Fragmentation / reassembly / ARQ — `link_layer.py`

* **Send:** encrypt (Fernet) → split into ≤180-byte chunks → for each fragment: send, wait up to
  `ack_timeout` (default 1.5 s) for the matching ACK, retry up to `max_attempts` (default 5), abort
  the whole message if any single fragment exhausts its retries (in-order delivery — a permanently
  missing middle fragment can't be skipped for an image/audio file).
* **Receive:** background thread listens on the UDP port GNU Radio forwards validated frames to;
  buckets fragments by `(src_id, msg_id)`; once all `frag_tot` fragments are present, concatenates,
  decrypts, and hands the result to the application via a callback tagged with `type`.
* **Stale reassembly cleanup:** buffers older than 30 s with missing fragments are dropped, so a
  message that will never complete (sender gave up) doesn't leak memory forever.
* **Known limitation (by design, for this project's scope):** stop-and-wait is one fragment in
  flight at a time — simple and easy to reason about/debug, but not fast. A 40 KB image at ~180
  B/fragment and, say, 150 ms/fragment round trip is on the order of 30 s. If you want to improve
  throughput, add a **sliding-window / selective-repeat** ARQ — same header format, no GRC changes
  needed, worth flagging in your report as a concrete "system performance reflection & improvement"
  (per the brief's outcome #4) rather than something to build under time pressure now.

## 8. Application layer — `flet_chat.py`

Same UI shell you already built (kept for the encryption bonus mark you'd already earned), now
backed by `link_layer.LinkLayer` instead of a bare socket:
* Text entry — unchanged UX, now fragmentation-safe for long messages.
* Image / audio: `ft.FilePicker` → read bytes → `link.send(peer_id, TYPE_IMAGE/AUDIO, data)` in a
  worker thread, with a per-fragment progress callback driving a progress bar on the sent bubble.
* Incoming messages are dispatched by `type`: text renders as a bubble, image renders inline
  (`ft.Image`), audio renders as a small player (`ft.Audio`).

## 9. Bring-up / test plan

1. **Single node, RF loopback** (attenuator/cable between TX and RX SMA, or two nodes on a bench a
   metre apart at low TX gain): confirm the constellation sink shows a clean QPSK cross and
   `digital_crc32_async_bb` passes frames — this alone reproduces the **mid-evaluation** (simplex
   text, one direction).
2. **Two nodes, FDD:** bring up Node 2, confirm ACKs return and `link_layer.py` reports delivery.
   This is the **final-evaluation core layer** (two-way, addressed, CRC-checked, ACKed).
3. **Fragmentation:** send a small image (<1 KB) first, then a full-size one, to shake out
   reassembly bugs before debugging RF issues at the same time.
4. **Range/robustness pass:** increase distance/attenuation, log per-fragment retry counts —
   this data is your "reflect on system performance" material (outcome #4).

## 13. Verification checklist before first RF test

I generated the `.grc` files by hand from your own working blocks wherever a verified parameter
schema existed. Two blocks are best-effort reconstructions and should be checked in the GRC GUI
the first time you open each file:

- [ ] **IIO Pluto Source** (RX chain, both files): confirm `URI`, `Frequency`, `Sample Rate`,
      `Bandwidth` show the intended values, and the gain-control field is set to **Manual** or
      **Slow Attack** (not left at a stale default) — open the block's properties dialog and check.
- [ ] **RRC matched filter**: not included in the generated files (see §3) — drag **"Root Raised
      Cosine Filter"** from the Filters palette into the RX chain between the DC Blocker and Symbol
      Sync, `alpha=0.35`, `sym_rate=samp_rate/sps`, before your first real range test.
- [ ] Any embedded Python block (`epy_block_*`) showing a warning icon on first open: click it once
      to force GRC to re-parse `_source_code` and regenerate its port cache — this is normal for
      hand-written `.grc` files and isn't a sign anything is actually broken.
- [ ] `tx_freq` / `rx_freq` — confirm against your lab's assigned frequency slot(s), not the
      433.0 / 438.0 MHz placeholders.
- [ ] `pluto_uri` — set to each physical ANTSDR E200's actual IIO context URI (`ip:192.168.1.10` is
      only correct if both nodes literally share that address, e.g. testing both flowgraphs against
      one unit on the bench).
- [ ] `MAX_FRAG_PAYLOAD = 180` appears in **two** places (`link_layer.py` and the `Frame Trim`
      `epy_block`'s embedded source) — if you ever change one, change both.
